# weeklist_check — 周版本清单检查

根据用户提供的需求单号列表，检查 GPM 中对应的需求单、任务单是否挂在指定版本树中，
修正版本/版本树不匹配的单子，移出多余单子到储备版本。

## 输入

- **需求单号列表**（必填）：如 `202606093472` `202606093473` …
- **目标版本树**（必填）：如 `0611`
- **目标版本**（可选，默认与目标版本树对应的版本）：如 `2026年6月11日`

## 执行流程

### 步骤 1：查 GPM 中匹配需求单号的单子

用标题搜索方式，在 GPM 中查找标题包含各需求单号的单子。

```bash
# 单个需求单号搜索（优先用 --size 拉大列表再 grep）
python3 -m gpm issue list --size 500 2>&1 | grep "<需求单号>"
```

找出的单子分三类：
- **需求开发单**：issueTypeId=1035
- **子任务单**：issueTypeId ∈ {1030,1031,1032,1033,1036,1037,1038,1039}
- 不关心其他类型（如缺陷）

**步骤 1 检查结果分类**：

| 类型 | 条件 |
|------|------|
| A正确 | 单子存在，且 version + versionTree 都在目标版本/版本树中 |
| B错版 | 单子存在，但 version 或 versionTree 不在目标版本/版本树中 |
| C缺失 | 需求单号找不到对应的 GPM 需求单或任务单 |

### 步骤 2：查目标版本树下的多余单子

列出目标版本树下所有单子，检查哪些不在需求单号列表中。

```bash
python3 -m gpm issue list --size 500 2>&1
# 筛选 versionTree 为目标版本树的单子
```

对每个单子，通过标题判断：
- 标题中包含数字串（如 `20260609xxxx`）→ 尝试提取需求单号
- 标题中无需求单号格式 → 独立单子

**步骤 2 检查结果分类**：

| 类型 | 条件 |
|------|------|
| D多余 | 标题含需求单号，但该需求单号不在用户提供的列表中 |
| E独立 | 标题不含需求单号格式（独立单子），默认不改 |

### 步骤 3：展示检查结果并确认

按以下格式展示所有检查结果：

```
需求单号  | GPM单子编号+标题  | 检查结果 | 处理方案
```

**处理方案**：

| 类型 | 处理方案 |
|------|---------|
| A正确 | 匹配正确，无需处理 |
| B错版 | 将单子的 version 和 versionTree 改为目标版本/版本树 |
| C缺失 | 走建需求单流程（复用 gpm-mjs skill），版本和版本树设为目标版本/版本树 |
| D多余 | 移出到储备版本（见移出版本策略） |
| E独立 | 独立单子，默认不改版本 |

### 步骤 4：用户确认后执行

用户确认后，按处理方案逐项执行：

**B 错版修正**：
```bash
python3 -m gpm issue update <issueId> --data '{"versionId":<目标版本ID>,"versionTreeId":<目标版本树ID>}'
```

**C 缺失建单**：复用 gpm-mjs 建单流程，版本和版本树指定为目标。

**D 移出**：按移出版本策略修改 version + versionTree。
```bash
python3 -m gpm issue update <issueId> --data '{"versionId":<储备版本ID>,"versionTreeId":<储备版本树ID>}'
```

### 步骤 5：执行后展示最终状态

```
需求单号  | GPM单子编号+标题  | 检查结果
```

最终检查结果：
| 类型 | 条件 |
|------|------|
| 匹配 | 需求单号有，GPM单子有，版本正确 |
| 独立单子 | 需求单号无，GPM单子有（版本未改） |
| （不应存在） | 需求单号有但GPM单子无或版本不对 → 说明执行有误 |

## 移出版本策略（D 多余单子）

根据单子内容判断目标储备版本：

| 单子特征 | 储备版本名 | versionId | versionTreeId | 说明 |
|---------|-----------|-----------|---------------|------|
| 武将、技能相关 | 储备武将 | 271 | 481 | 公测根节点，不填子版本树 |
| 皮肤、资源相关 | 储备皮肤 | 280 | 481 | 同上 |
| 程序框架、逻辑优化、底层重构 | 储备技术优化 | 276 | 481 | 同上 |
| 策划设计、系统功能优化/调整 | 储备系统 | 277 | 481 | 同上 |

> **注意**：「无次版本」= versionTreeId 设为公测根节点 **481**（不选子版本树如0611/0618等），同时 versionId 设为对应储备版本。
> 无法归类时默认归入「储备系统」(277)，versionTreeId 同样为 481。

**判断关键词**：

- **武将/技能**：武将名、技能名、spine、武将接入、武将重制
- **皮肤/资源**：皮肤、手牌皮肤、美术资源、UI资源、贴图、模型
- **技术优化**：框架、重构、性能优化、底层、SDK、架构
- **系统策划**：排行榜、赛季、活动、商店、充值、义旗、宝箱、优化、调整、功能

## 版本树与版本对应关系

常用版本树 → 版本映射（以 `python3 -m gpm version-tree list` 和 `python3 -m gpm version list --all` 实时查为准）：

**储备版本**（versionTreeId = 481 公测根节点，不填子版本树）：

| 储备版本 | versionId | versionTreeId | 说明 |
|---------|-----------|---------------|------|
| 储备武将 | 271 | 481 | 武将/技能相关需求储备 |
| 储备皮肤 | 280 | 481 | 皮肤/美术资源储备 |
| 储备技术优化 | 276 | 481 | 底层优化/框架重构 |
| 储备系统 | 277 | 481 | 策划设计/功能调整 |

> ⚠️ versionId 以实时查询 `python3 -m gpm version list --all` 为准，可能变更。

## 实现要点

1. **先全量拉取再匹配**：`python3 -m gpm issue list --size 500` 一次拉够，用 Python 脚本在内存中匹配，避免逐条 API 调用。
2. **标题匹配**：GPM 单子标题格式为 `{需求单号} {需求名称}` 或 `{需求单号} {任务名称}`，用 `需求单号 in summary` 判断。
3. **版本树匹配**：比较 versionTreeId 是否等于目标版本树 ID。
4. **版本匹配**：比较 versionId 是否等于目标版本 ID。
5. **展示时合并同类**：同一需求单号下的需求开发单和子任务放在一起展示。
6. **独立单子默认不改**：E 类单子不出现在最终确认表中，仅在执行后汇总中提到。
7. **缺版本树 ID 时实时查**：用 `python3 -m gpm version-tree list` 和 `python3 -m gpm version list --all` 获取最新 ID。
