# Bug 修复流程

## 概述

结构化 Bug 修复流程：先只读诊断（使用 investigate skill），再 TDD 修复（使用 test-driven-development skill），最后强制记录教训（使用 self-improvement skill）。

## 触发条件

用户提到以下任一关键词或语义模式时触发：

**直接关键词：**
- "修复 bug"、"fix"、"某个功能坏了"、"出 bug 了"
- "XX 不对"、"XX 有问题"、"XX 报错了"
- "回退一下"、"regression"

**语义模式（满足任一组合即触发）：**
- 包含"错误" + 包含"规则/检查/验证/测试" → 如"检查出错误"、"规则报错"
- 包含"矛盾" + 包含"比较/判断/逻辑/结果" → 如"结果自相矛盾"、"逻辑矛盾"
- 包含"不一致" + 包含"时间/日期/数值/配置" → 如"时间不一致"
- 包含"误报" / "误判" / "错误触发" → 如"相等时间被误报"
- 包含"应该通过却报错" / "应该报错却通过" / "结果不对" / "结果有误"
- 包含"发现" + 包含"问题" + 包含"检查/规则/验证" → 如"检查发现2个问题"

**不要触发：**
- 用户只是要求解释代码、配置环境、优化查询、写新功能等与 bug 修复无关的请求

## 与其他 skill 的关系

| 阶段 | 使用的 skill | 说明 |
|------|-------------|------|
| 诊断 | `investigate` | 只读调查，定位根因，等待用户确认 |
| 修复 | `test-driven-development` | 红-绿-重构循环，TDD 模式修复 |
| 记录 | `self-improvement` | 记录错误教训，防止同类问题复发（强制步骤，不可跳过） |

本 skill 是调度者，协调上述三个 skill 的执行顺序。

## 执行流程

### 分支判断：用户是否明确要求修复？

**如果用户只报告问题/现象，未明确要求修复：**
1. 执行步骤 1（诊断）
2. 向用户报告根因假设和修复方案
3. **等待用户明确说"开始修复"或"修吧"后再进入步骤 2**
4. 用户确认后，依次执行步骤 2-6

**如果用户明确要求修复 bug：**
1. 依次执行步骤 1-6

---

### 步骤 1：诊断 Bug（使用 investigate）

**开始前先查记忆**：
```
1. 调用 mempalace_search 查询：
   - 关键词：涉及的模块/功能名、错误现象、相关文件名
   - 检查是否有历史同类 bug 记录、已验证的根因模式
2. 调用 claude-mem 查询（通过 /mem search 或查看历史摘要）：
   - 搜索：该模块近期会话中的 bug 修复记录
   - 检查 .learnings/LEARNINGS.md 中的历史教训
3. 调用 forgetful query_memory 查询：
   - 搜索：项目架构知识、已知代码问题、模块设计约束
   - 检查是否有已记录的"常见陷阱"或"架构限制"
- 如有记录，优先参考历史经验加速定位
```

进入只读调查模式：
1. 阅读 bug 描述，定位相关代码文件
2. 使用 Grep/Read/Glob/LSP 收集信息（**禁止修改代码**）
3. 提出根因假设和影响范围
4. 向用户报告发现，**等待确认**

**输出**：简要说明 bug 根因、涉及的文件和预计影响范围。

---

### 步骤 2：TDD 修复（使用 test-driven-development）

用户确认后，进入 TDD 修复模式：
1. **红灯**：编写能复现 bug 的 failing test
2. **验证红灯**：运行测试确认失败
3. **绿灯**：只修改必要的代码让测试通过（不做额外重构）
4. **验证绿灯**：运行测试确认通过 + 相关模块回归测试
5. 修复后添加必要的中文注释

#### 2.1 验证仓库上下文（强制）

修改任何文件前，必须执行：
```bash
git rev-parse --show-toplevel  # 确认当前仓库根目录
git branch --show-current      # 确认当前分支
```

**如果当前是 worktree：**
- 使用 worktree 的绝对路径编辑文件
- 禁止修改主仓库目录的文件

#### 2.2 红灯：编写能复现 bug 的 failing test

#### 2.3 验证红灯：运行测试确认失败

#### 2.4 绿灯：只修改必要的代码让测试通过（不做额外重构）

#### 2.5 验证绿灯：运行测试确认通过 + 相关模块回归测试

#### 2.6 验证修改位置（强制）

修改完成后必须执行：
```bash
git diff --stat  # 确认变更落在当前 worktree
```

**如果变更落在错误位置（如主仓库而非 worktree）：**
1. 回滚错误位置的修改
2. 将 patch 应用到正确的 worktree
3. 重新验证

#### 2.7 修复后添加必要的中文注释

---

### 步骤 3：补充测试覆盖

修复验证通过后，补充完整的测试覆盖：

1. **Bug 复现测试**（步骤 2 创建的）
   - 确保测试名和注释清楚记录 Bug 细节
   - 包含 Bug 发现日期、线上影响、根因分析

2. **修复验证测试**（新增）
   - 正向场景：修复后正确配置不应误报
   - 边界场景：临近阈值（如时间窗口边界值）
   - 多实例场景：多个受影响对象独立检测

3. **测试注释规范**

   每个 Bug 复现测试的注释必须包含：
   ```
   // TestXxx_BugReproduce
   // 复现 Bug：[简要描述]
   //
   // Bug 详情（[发现日期] [来源]）：
   //   - 根因：[代码层面的具体原因，包含文件名和行号]
   //   - 影响：[受影响的功能范围]
   //   - 修复：[具体修改内容]
   ```

4. **测试数据工厂**
   - 提取可复用的测试数据构建函数，参数化关键变量
   - 避免每个测试都重复构造完整数据

---

### 步骤 4：同步文档

- 如果修复涉及接口变更或行为变更，更新相关文档
- 代码修改同步更新注释

---

### 步骤 5：记录教训（使用 self-improvement）【强制，不可跳过】

**无论 fix-bug skill 是否被显式触发，只要修复了 bug，必须执行此步骤。**

将本次 bug 的根因和修复方案记录到 `.learnings/`，防止同类问题复发。

**记录内容必须包含：**
- 根因：代码层面的具体原因（文件名、行号、逻辑错误）
- 影响：受影响的功能范围、用户场景
- 修复：具体修改内容
- 预防：如何避免同类问题再次发生

**如果 .learnings/ 目录不存在，先创建。**

---

### 步骤 6：提交

1. 确认所有修改在正确的 worktree 中
2. `git add` 相关文件
3. 编写描述性提交消息（捕获更改的完整范围）
4. `git commit`

---

## 红线

- 不允许跳过诊断直接修复
- 不允许跳过测试直接修复
- 不允许说"应该修好了"而不运行验证
- 不允许"顺手"重构无关代码
- 不允许把多个 bug 的修复混在一起
- **不允许跳过 self-improvement 记录**
- **不允许在 worktree 中修改主仓库文件**
- **修改后必须验证变更位置（git diff --stat）**

## 示例

```
用户：seasonPass 英雄验证规则跳过了过期赛季

Claude：
1. [investigate] 定位：rain-excel-checker/xlsx/coded_rules/season_pass_hero.go
   - 发现：过期赛季判断逻辑错误地跳过了检查
   - 影响：所有过期赛季的英雄验证被静默跳过
   - 等待用户确认...
2. [test-driven-development]
   - 验证仓库上下文：git rev-parse --show-toplevel / git branch --show-current
   - 红灯：TestSeasonPassExpiredSeasonSkip → FAIL
   - 绿灯：移除过期赛季跳过逻辑 → PASS
   - 回归：go test ./xlsx/coded_rules/... → all PASS
   - 验证位置：git diff --stat → 确认在 worktree 中
3. 补充测试：
   - TestSeasonPassExpiredSeason_BugReproduce（带完整 Bug 注释）
   - TestSeasonPassExpiredSeason_ValidConfig_NoError（正常配置不误报）
   - TestSeasonPassExpiredSeason_MultipleSeasons（多赛季独立检测）
4. [self-improvement] 记录到 .learnings/LEARNINGS.md
5. git commit
6. 完成
```
