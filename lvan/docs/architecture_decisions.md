# LVAN Dumper 架构设计决策记录

## 文档目的
记录 LVAN Dumper 工具架构设计过程中的关键决策及其背后的原因，为后续开发提供参考。

## 背景
LVAN Dumper 是一个外网数据克隆工具，支持数据库的 dump 和 import 操作。当前需要优化以支持：
1. 多数据源支持 (MySQL, Redis, 未来扩展)
2. MySQL dump SQL模板导出
3. 更多导出格式支持
4. Blob数据的优化处理

## 关键架构决策

### 1. 数据源接口设计决策

#### 决策内容
采用 **双版本实现策略**：
- v1目录：函数式接口实现
- v2目录：访问者模式实现

#### 设计方案

**函数式接口 (v1)**
```go
type Datasource interface {
    Accept(fn func(DatasourceAccessor))
}

type DatasourceAccessor interface {
    GetMetadata() Metadata
    Dump(where string, ids []string) [][]map[string][]byte
    Import(data [][]map[string][]byte)
    Type() string
}
```

**访问者模式 (v2)**
```go
type Datasource interface {
    Accept(visitor Visitor)
}

type Visitor interface {
    VisitMySQL(ds *MySQLDatasource)
    VisitRedis(ds *RedisDatasource)
}
```

#### 决策原因

**选择函数式接口的原因：**
- 实现简单，符合直觉
- 添加新数据源类型不需要修改接口
- 代码简洁，易于理解和维护
- 更灵活的操作定义

**选择访问者模式的原因：**
- 双重分派，提供编译时类型安全
- 扩展新操作容易，只需添加新的Visitor
- 符合标准的设计模式实现
- 更强的类型约束

**同时维护两种版本的原因：**
- 充分对比不同架构的优劣
- 验证不同场景下的适用性
- 为未来架构选择提供实证数据
- 保持技术探索的灵活性

#### 接口设计原则
- **只负责参数解析**：接口仅处理数据源参数的解析
- **自动连接管理**：连接的创建和关闭完全封装在内部
- **专注数据访问**：不暴露连接管理逻辑给外界使用
- **分离关注点**：Dump和Import逻辑不在数据源接口中

### 2. 命令行架构决策

#### 决策内容
沿用现有的 **Cobra + Viper** 架构，采用子命令方式管理不同数据源。

#### 命令结构
```
connect mysql dump  [mysql specific flags]
connect mysql import [mysql specific flags]
connect redis dump  [redis specific flags]
connect redis import [redis specific flags]
```

#### 决策原因
- **保持一致性**：与现有代码架构保持一致
- **参数隔离**：不同数据源的参数定义在各自的子命令上
- **配置复用**：继续使用Viper的配置文件和环境变量支持
- **向后兼容**：不破坏现有的使用习惯
- **扩展友好**：添加新数据源只需增加新的子命令

### 3. 测试策略决策

#### 决策内容
使用 **同一套单元测试** 同时验证 v1 和 v2 两种实现。

#### 测试架构
```
pkg/datasource/
├── tests/           # 共享测试套件
├── v1/             # 函数式接口实现
└── v2/             # 访问者模式实现
```

#### 决策原因
- **行为一致性**：确保两种架构产生相同的结果
- **质量保证**：通过统一测试验证实现正确性
- **性能对比**：可以在相同测试条件下对比性能
- **维护效率**：避免重复编写测试用例
- **回归防护**：防止一个版本的修改影响另一个版本

### 4. Blob数据处理策略决策

#### 决策内容
采用 **多策略自动选择** 的Blob数据处理方式。

#### 处理策略
1. **内联存储**：小于1KB的数据直接存储
2. **Base64编码**：1KB-1MB的数据使用Base64编码
3. **外部文件**：大于1MB的数据存储到外部文件

#### 格式特定策略
- **JSON格式**：小数据hex编码，中等数据base64，大数据外部引用
- **CSV格式**：强制外部文件存储
- **YAML格式**：支持块格式的Base64编码

#### 决策原因
- **性能优化**：根据数据大小选择最优存储方式
- **格式兼容**：不同格式有不同的最优策略
- **用户体验**：避免因数据过大导致文件无法打开
- **灵活性**：支持配置驱动的策略调整

### 5. MySQL Dump SQL模板系统决策

#### 决策内容
实现基于 **Go template引擎** 的SQL模板系统，支持强大的变量替换和自定义函数。

#### 模板特性
- Go template语法支持
- 丰富的内置函数库
- 配置驱动的变量管理
- 针对Blob数据的特殊处理

#### 决策原因
- **标准化**：Go template是成熟稳定的模板引擎
- **灵活性**：支持复杂的条件判断和循环
- **可扩展**：自定义函数满足特定需求
- **易维护**：模板文件与代码分离，便于修改

### 6. 新格式支持优先级决策

#### 决策内容
按 **实用性和需求优先级** 安排格式支持顺序。

#### 优先级排序
1. **高优先级**：JSON, CSV (2-3周)
2. **中优先级**：SQLite, YAML (4-6周)
3. **低优先级**：Parquet, Protobuf, MessagePack, Avro (长期规划)

#### 决策原因
- **广泛需求**：JSON/CSV是最常用的数据交换格式
- **工具兼容**：Excel/电子表格广泛支持CSV
- **渐进实施**：从简单到复杂，降低开发风险
- **资源优化**：优先满足最紧迫的需求

### 7. 目录结构组织决策

#### 决策内容
采用 **功能模块化** 的目录结构设计。

#### 目录结构
```
pkg/
├── datasource/
│   ├── v1/              # 函数式接口
│   ├── v2/              # 访问者模式
│   ├── tests/           # 共享测试
│   └── common/          # 共享代码
├── blob/                # Blob处理
├── template/            # 模板系统
├── format/              # 导出格式
└── core/                # 核心逻辑
```

#### 决策原因
- **职责清晰**：每个模块有明确的功能边界
- **版本并行**：v1和v2可以并行开发和测试
- **代码复用**：common目录减少重复代码
- **易于扩展**：新功能可以独立模块形式添加
